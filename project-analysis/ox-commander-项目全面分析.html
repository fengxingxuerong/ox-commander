这不是纸面判断，是本机真实的执行结果：

  Property 'deletions' does not exist on type 'BatchGuard'.

2.1 分层与依赖方向

值得学习的设计：分级落地「分层红线」

shared/ 的分层约束有一条真实机制：eslint.config.mjs 给 shared/**/*.ts 配了 no-restricted-imports，禁 node:* 与裸 node 内建、 禁 electron|react|react-dom|zustand、禁反向依赖 ../electron/** 等。 落地时该层对外 import 数为 0，属零违规的纯增量，只拦未来。

但作者没有把这个规则无脑套到 headless/**，理由写在注释里： run-spec.ts 经 electron/platform 已把 electron/sandbox 拉进来， 加规则当场就红。这种「先承认现状、不靠规则硬压」的处理比强行统一更可靠。

2.2 一次 run 的端到端数据流

两个入口 Electron：orchestration:planning → generatePrd → decompose （落 ProjectStore.batchesJson）→ orchestration:start → execute runningProjectId 是单飞闸；renderer 只有一条事件通道 ox:event headless：stdin 全量 JSON → parseSpec → runSpec → stdout JSONL 退出码 0=delivered / 2=repair 耗尽 / 1=fatal 六阶段（代码控制，LLM 不能改写阶段序列） PRD → PLANNING → DEVELOPMENT → VERIFICATION → DELIVERY → DONE ↑____________ repair loop（按 zone 归因重修）____________| 三处落盘点（都走 writeFileAtomic） 1. checkpoint journal：计划完成 / 每批 / 每轮收尾 2. 审计 JSONL：run-start / run-end（仅桌面有；headless 改发协议事件） 3. 快照备份 <userData>/snapshots/<runId>（内容备份，不用 git stash）

2.3 编排引擎（electron/engine/orchestrator.ts，798 行）

六阶段与 repair loop

阶段推进由代码硬控。核心循环在 runPipeline：

while (round <= maxRounds + extraRounds) {   // orchestrator.ts:509
  assertWallClock()                          // :510  墙钟上限
  await this.gate()                          // :511  暂停闸
  ... 逐批 runBatch ...
  onStage("VERIFICATION")                    // :621
  if (!anyDevFailure && report.passed) { ...DELIVERY... }   // :641
  routeVerificationErrors(...)               // :676  按 zone 归因
}

设计亮点：动手前先跑基线（orchestrator.ts:472-503）

在派发任何任务之前，先把同样的验证命令跑一遍。若目标项目本来就红着，会给每份重修上下文 附上 [本次运行前就已失败] 标记。

解决的问题很实际：智能体看到一份与自己无关的失败，会去修不属于自己的东西；而引擎的 「验证未过但无失败任务 → 全员重跑」分支会把同一份失败再烧三轮预算。标注之后，谁造成的谁负责。

代价是每次运行多一轮验证命令（verifier 首败即停，所以基线只报出第一条红）。 换的是归因与预算，不是速度 —— 作者自己把这个权衡写明了。

错误按 zone 归因

routeVerificationErrors(report, pendingNow, projectRoot)（:676）把验证错误 路由到「拥有失败文件的那个 zone」，每个任务只看到自己该负责的错误（外加无法归因的），而不是整份日志。 这是 repair loop 能定向重修的前提。

几处务实的状态处理

  • 取消不留悬挂任务（:326-347）：cancel 时 inFlight 里的任务补发 cancelled 终态，否则看板会一直转圈。
  • 用量三条出口都上报（:341-346）：成功 / 取消 / 抛错都取一次快照，理由是 「失败的运行一样烧了 token，只在成功路径上报会让最贵的那次恰好看不见」。
  • 被跳过的上游只给一次机会（:539-555）：用户跳过的任务，其下游缺的产物永远不会出现， 追加重修轮是纯烧钱 —— 试过一轮后不再派发，且只播报一次。
  • 断点续跑不跑基线（:486）：工作区已被上一轮改过，「基线」概念不成立。
  • 环节重试幂等：竣工验收 [383] failed 之后又来 completed 时仍算失败 —— 失败不能被后续事件洗白。

发现的问题

中「零验证命令」会静默放行 —— verifier.ts:181 用 results.every(r => r.ok) 判定，空数组时 every 返回 true。

作者已意识到并做了缓解：verifiedFieldsFor（orchestrator.ts:364-374）要求 report.results.length > 0 才算 verified，日志也会喊「本次交付未经构建/测试验证」。 但判定本身是 passed，任务会进入 DELIVERY。

定性：纯文档类项目确实是合法配置（headless 协议允许空集），所以这是「有意的语义 + 已加固的说法」， 不是纯缺陷。但如果宿主误配了空验证命令，引擎不会阻拦，只会在日志/凭据里说明。

2.4 调度器（scheduler.ts，671 行）

设计亮点：批内互斥判据从「同名」升级为「重叠」

scheduler.ts:398-404 对收到的批次做两两校验，重叠即 throw：

if (zonesOverlap(zones[i], zones[j])) throw new Error("zone conflict inside batch: …")

注释（:395-397）写明这是修过的语义：原实现只做字符串全等， 于是 zone src 与 src/util 会同批并发写同一目录，而越权检测看不见 —— 因为每条写入都落在本批某个 zone 之内。

并发度由四层叠加：

  1. 平台级槽位：maxParallel() 默认 4（:29），FIFO 移交（:182-189）
  2. 429 节流闸：awaitThrottle()，指数退避 base 30s / cap 300s（:242-261）
  3. agent 级并发声明：admitConcurrency(...)（:347）
  4. 冗余赛马：raceRedundancy > 1 时再取 redundancy-1 个执行器（:451-459）

中no-router 回退路径绕过并发准入

scheduler.ts:328 的 available[i % available.length] 只过 admitBreaker，不过 admitConcurrency；而 router 路径（:347）会过。

触发条件：关闭能力路由（settings.agentRouter === false）＋ 某 agent 声明 maxConcurrency: 1 → 同批可被塞多个任务。

缓解事实：该回退路径只服务 legacy 池（无并发概念的池子在设计上恒可接）， 且 router.ts:150-158 的硬拦确实按声明生效。影响面限于「关掉 router 但池里混了声明式 agent」的组合。

中赛马输家的写入不参与回滚

scheduler.ts:481-488 把同一任务派给多个执行器，它们并发写同一 zone、同一 projectRoot。 输家在被 abort（:508-532）前写的文件既不会被回滚、也不会被隔离， 赢家的验证可能看到混合产物。

这与 batch-guard.ts:331-336 注释断言的「批内不可能并发写同一文件」前提直接冲突 —— 该前提对普通批次成立，对赛马不成立。

2.5 能力路由（router.ts，243 行）

硬拦先于打分：缺 tag → continue（:140）；role 不匹配（:141-142）； zone 不在候选 glob 内（:143-144）；circuit === "open"（:147）； 声明了 maxConcurrency 且满载（:155-158）。

打分权重（:59-68）：roleExact 100 / roleWildcard 60 / zoneScoped 40 / zoneBroad 20 / quality 20 / load 10 / circuitHalfOpen 15 / priority 1。

tie-break 顺序（:220-231）：声明能力者优先于 inferredLegacy 泛用者 → 分高者胜 → preferredAgents 顺序 → 原池顺序。

设计亮点：满载时如实报「没有 agent」，而不是硬塞

router.ts:198-217：能力不匹配时回落 legacy round-robin； 但合格候选全部满载时不回落，如实返回 agentId: undefined， 交修复轮重派。配合 :205-213 的「loadBlocked > 0 时拒绝 fallback」， 避免把任务硬塞回满载者。注释里还留了 2026-09-26 的实弹证据 （maxConcurrency=1 的 agent 在 t1 在飞时仍以 180+ 分接下 t2）。

中但软惩罚「扣分」用错了地方 —— 同一段有两个不同口径： :157 用 caps.maxConcurrency（已归一，最小 1）做硬拦， :188 的 load 扣分也用 caps.maxConcurrency。

而 shared/agent-contract.ts:212 的 normalizeCapabilities 已把 maxConcurrency 归一到 Math.max(1, Math.floor(caps.maxConcurrency || 1))， 因此除零/NaN 路径不可达。

这一条是我实测推翻的：子代理报告称此处会产生 NaN 导致排序不确定， 但按 agent-contract.ts:212 的归一化，maxConcurrency 最小为 1，该风险不成立。

2.6 仲裁层（batch-guard.ts，445 行）

四种冲突处置档，各自行为确实不同（此前 report-only 与 deny-all 曾共用一支）：

档位对 outcomes对磁盘备份remedy
report-only不改判不动commitpass
deny-all全部置 ok:false不动commitfail-batch
revert-batch（默认）全部置 ok:false按 allPaths 回滚commitrevert
quarantine全部置 ok:falserename 到 .ox-quarantine/commitquarantine

设计亮点：回滚只删「有 create 正面证据」的文件

batch-guard.ts:245 收集 create 记录传给 snapshots.revert； snapshot-store.revertOne 四步判据：

  1. 备份里有 → 拷回
  2. 没备份且当前不存在 → skipped（无需回滚）
  3. 没备份但存在、且 created 里没有它 → 保留现状不删
  4. 只有有正面证据才 rmSync

翻车形态写得很具体：根级 package.json 常在 zone 外，旧逻辑「备份里没有 ⇒ 新建 ⇒ 删掉」 会把用户文件删掉，且默认档下每轮重修再删一次。

不做 git、不做硬链接（snapshot-store.ts:59-83 文件头记录三条硬教训）： 硬链接会共享 inode，writeFileSync 原地截断会连备份一起改 —— 作者说实测「回滚恢复出新内容」。

设计亮点：越权删除台账（本次未提交改动正在做的功能）

解决的问题：report-only / deny-all / quarantine 三档都不恢复被删文件， 而下一批的基线从磁盘重建 → 同一次删除只响一次就消失，被删的源文件可静默一路带到交付。

实现：updateDeletionLedger（:103-128）是纯函数，三条规则 「销账看盘不看批 / 入账看盘不看报 / 首见批次不漂移」，且每条 settle 出口都结算 （含 clean 批，:201-215）—— 因为缺陷形态恰恰是「下一批干干净净，被删文件从此没人再提」。

3. 安全边界分析（重点：我用运行时探针实测过）

这一节的所有结论都来自实际执行 dist-electron 编译产物做的探针， 而非阅读推断。探针脚本为只读，未改动任何项目文件。

3.1 沙箱五件套

组件职责实测评价
PathPolicy路径判定（realpath 后七级）扎实，realpath 处理 junction 与 8.3 短名
CommandPolicy命令白名单 + 黑名单 + 元字符有真实绕过面（见 3.3）
TimeoutGatedeadline / idle 双超时idle 只对外部适配器开，内置执行器刻意忽略
CircuitBreaker连续失败熔断三态闭环，认证失败也计入（避免每任务再烧配额）

PathPolicy 实测结果

zone="src/"        : package.json=deny  package.json.=deny  .env=deny  .git/config=deny
zone="."           : package.json=deny  package.json.=ALLOW .env=deny  .git/config=deny
zone=""            : package.json=deny  package.json.=ALLOW .env=deny  .git/config=deny
zone=undefined     : package.json=deny  package.json.=ALLOW .env=deny  .git/config=deny
→ src/a.js=ALLOW(zone)   tests/b.js=deny(zone 越权)

结论子代理报告的「尾随点绕过保护文件」不成立，我实测推翻：

它推断 package.json. 会被 Windows 归一化到 package.json 从而覆盖清单文件。 实测：在 NTFS 上写入 guard.txt. 后，目录里同时存在 guard.txt（内容未变） 与 guard.txt. 两个条目 —— Windows 不再剥离尾随点，两条路径是两个文件。

安全性来自另一侧：PathPolicy 在 zoneMode: "legacy"（默认）下， zone = "" / "." / undefined 视为不受限（path-policy.ts:212-224）， 所以 package.json. 只会在「zone 本身就等于全树」时才被放行 —— 那时 package.json 本身被 forbidden 拦住，而 package.json. 是另一个文件、 不改原文件。不构成覆盖。

中但有一个真实且更值得注意的语义：zone 不受限 = 全树可写

默认 zoneMode: "legacy"（path-policy.ts:150），此时 zoneIsUnrestricted 对 "" 与 "." 都返回 true（:212-217）。

后果是双重失效：写入侧全树放行，而 BatchGuard.detect 的 zones.some(z => isInsideZone(c.path, z))（:339）对全树 zone 恒真 → 四档仲裁全部变成 no-op。

缓解：正常规划路径下 zone 来自 PRD 产物路径，不会退化成 ""/"."； 且 forbiddenWrite（package.json / .env / .git/** / node_modules/**）是独立于 zone 的硬地板，实测在四种 zone 下全部 deny。 所以这是纵深防御的「第二层默认关闭」，不是裸奔。

3.2 CommandPolicy 实测结果

ALLOW  node ["x.js"]                     ← 正常
ALLOW  /tmp/xxx/node.cmd ["x.js"]        ← basename 冒充
ALLOW  /tmp/xxx/node ["x.js"]            ← 同上
ALLOW  /usr/local/bin/eslint.bat ["x"]   ← 同上
ALLOW  vitest.com ["run"]                ← 同上
ALLOW  npm ["run","build"]
ALLOW  git ["commit","-m","x"]           ← commit 未禁
DENY   powershell / curl                 ← 黑名单生效
DENY   node ["-e","1"]                   ← eval flag 生效
DENY   python ["-c","1"]                 ← eval flag 生效

元字符集合边界：
ALLOW  a"b   ALLOW a(b)   ALLOW a=b   ALLOW 100%
DENY   %PATH%   DENY a!b   ALLOW a'b   ALLOW a,b

高绕过面 1：命令名前缀无关 —— 任意目录下的同名文件都被当作白名单命令

command-policy.ts:173-177 的 baseName 只取路径末段并剥一个扩展名， 完全不限制可执行文件的所在路径。实测把文件命名为 node.cmd 放在任意临时目录， check() 即返回 ALLOW。

触发条件：智能体在自己 zone 内可写文件（path-policy 允许），把恶意脚本命名为 node.cmd / eslint.bat，再以路径形式调用 → 以白名单名义执行任意程序。

高绕过面 2：白名单只约束「解释器名」，不约束「解释什么」

EVAL_FLAGS（:147-152）只拦 node -e/-p 与 python -c， 而 node / python / make / cargo / gradlew / dotnet 都在白名单里。

智能体只需在自己 zone 内写一个 x.js，随后 node x.js 即等价于「以用户权限在宿主执行任意代码」。 而验证/冒烟命令本身就来自大脑生成的产物（verifier.ts:195-202 注明「命令来自 decompose 产物」）。

作者在 README 里已经明说这一层：「沙箱不管网络……命令黑名单里有 curl/wget/nc， 但 node 在白名单里 —— 智能体自己发 HTTP 请求是拦不住的」。这是已知且公开声明的边界， 但对使用者而言，这意味着沙箱的真实定位是「防误伤」而非「防恶意」。

中绕过面 3：npm run <script> 任意脚本不设防

denyNpm 只拦 publish/adduser/login/logout/token/config， install/add/run/test/exec 全部放行。而 package.json 的 scripts 段一旦被改写， npm run x 即执行任意命令 —— 命令策略看不到脚本正文。

缓解：package.json 在 DEFAULT_FORBIDDEN_WRITE 里，实测 deny； 且 action-gate.ts 的跨动作状态机在批次内观察到依赖安装痕迹后会把 npx 升级为拒绝。

中验证结论可被判定的对象伪造

verifier.ts:286 用正则 /\n\[exit\](\d+)/ 取第一个匹配， 而标记是追加在子进程日志之后的。我实测复现：

stdout = "BOOM: 我失败了\n[exit]0" + "\n[exit]1"（真实退出码 1）
解析  → exitMatch[1] === "0"  → 判定「通过」

冒烟检查只要打印一行 [exit]0（并可自行补上 expectContains 片段）即可自证通过 —— 而冒烟层的存在意义正是「防自证盲区」。

触发门槛不低（需要模型主动写这行），但这是判定可被被判定方伪造这类问题，修法也简单： 取最后一个匹配，或改用 child.on("close", code) 的真实退出码。

3.3 凭证与数据外泄面

做得好的部分

  • scopedEnv()：验证与冒烟子进程、CLI 智能体都走最小化环境，默认拿不到宿主其他 provider Key
  • 审计只记变量名不记值（droppedSecretNames），避免审计日志成为第二泄漏面
  • 快照侧双层凭据拉黑：walk 时拉黑 + 读取时二次过滤（sensenova-api.ts:41-66, 120-121）
  • 工作区快照有体积闸门：单文件 4000 字符、总量 32000 字符

中工作区文件正文会原样发往第三方 LLM 端点

sensenova-api.ts:41-44 的注释自己写明：「快照 = 发往第三方 LLM 端点的项目内容。 凭据类文件一旦入快照就等同于外泄」。

防护建立在文件名启发式上（:46-59 的 12 条正则，按 basename 小写匹配）： 命中 .env 家族、rc 文件、id_*、证书后缀、含 api-key/secret-key/password/credential 的名字。

因此 src/config/prod.json、data/customers.csv、deploy/values.yaml 这类「名字无害」的敏感文件会被整段发出去。触发条件：仓库里存在名字不像凭据的敏感实体。

中maxTokensPerRun 是软上限，不具备阻断能力

  • headless/protocol.ts:104 字段注释自称软上限
  • :285-295 解析期只校验「必须是正数」，不与任何运行期计量联动
  • 执行器侧 meteredLlm 是调用后累计，且只有自建 client 被包装 （sensenova-api.ts:76-84 解释了为什么不能重复包：注入方自己会包一次）

结论：它是「用量上报 + 事后告警」，不是预算闸门。宿主注入自己的 client 时， 执行器消耗甚至不进这个 meter。

值得肯定：作者没有假装管住了，而是把盲区写进契约注释并在看板上念出来（budgetBlindNote）。 工程诚实度高于多数项目。

提示headless serve 形态：无鉴权、无 TLS

serve.ts:13-22 明确声明刻意不做鉴权、不做任务队列、不内嵌看板； serve-main.ts 无 TLS 配置。README 也警告「本机/内网/SSH 隧道后用」。

触发条件：绑到非 loopback 地址 → 任意可达方可读 /state、订阅 /events （含路径、阶段决策、用量）、并 /pause /resume 干预运行。 属于已声明的设计取舍，但部署时必须受网络层保护。

设计亮点：统一契约 + 统一事件出口收掉了最容易出竞态的语义

shared/agent-contract.ts 定义统一契约（AGENT_PROTOCOL_VERSION = "ox-agent/2"）， electron/agents/run-session.ts 的 RunSession 把「并发、取消、终态不丢」收在单一实现里： push() 在 run 结束后只丢 log 而保留终态事件；wake() 是唯一唤醒入口。 三类适配器复用它，适配器作者不需要各自处理「幻醒 / 丢事件」。

设计亮点：超时三层分层，并点名反模式

sensenova-api.ts:94-101 的注释直接点出反模式： 「一次慢请求吃光整轮预算、failover 拿不到第二次机会」，所以： 单请求 EXECUTOR_TIMEOUT_MS = 300s、整轮 runDeadlineMs = 600s、 大脑层 BRAIN_TIMEOUT_MS = 120s，三者不可混用。

更细的一处：该适配器刻意忽略 idleTimeoutMs（:85-93）， 理由是它在单次请求期间零事件，idle watchdog 会在每次「慢但健康」的生成上误杀 （一次请求在途最长 300s 期间本来不产生事件）。这个取舍有明确论证，不是遗漏。

低契约字段与实现落差：idleTimeoutMs 被静默忽略且不暴露

契约（agent-contract.ts 的 DEFAULT_AGENT_LIMITS）提供了该字段， 实现只兑现 runDeadlineMs，而 capabilities() 并不把「部分兑现」这件事告诉调度方。 宿主设了 idleTimeoutMs 会以为生效。

4.2 LLM 线路池与故障转移

线路条数怎么算

线路池 = SENSENOVA_MODELS(4) × SENSENOVA_KEY_VARS(3) = 12 条
       + AMD_API_KEY → amd-radeon（DeepSeek-V4-Flash）= 1 条
       = 13 条

SENSENOVA_MODELS_EXTRA（kimi-k3）刻意不进默认轮转，有测试守着这一点。

本机 .env 里实际配了 5 个 key 变量（3 把 SenseNova + AMD + NVIDIA）， 但 NVIDIA 不在默认 provider 表中 —— 因为项目文档记录其实测「280s 无响应」。

设计亮点：对端异常的资源攻击被全面加上界

RETRY_AFTER_COOLDOWN_CAP_MS = 300_000   // 冷却时长封顶 5 分钟
RETRY_AFTER_SLEEP_CAP      = 60_000     // 单次休眠封顶 60s（防超大 retry-after 睡死调用方）
ERROR_BODY_BYTE_CAP        = 64KB       // 错误体有界读取
RESPONSE_BODY_BYTE_CAP     = 8MB        // 响应体有界读取
maxStdoutBytes             = 2 MiB

即「服务端给再大的 retry-after / 再大的 body 也拖不死、撑不爆平台」。 全线路冷却时显式抛 AllRoutesCoolingError，有界失败而非无限等待。

429 只冷却命中线路本身，请求立即落到同 key 其他模型 → 其他 key → 其他 provider。

中capabilities().maxConcurrency 口径不一致

注释（sensenova-api.ts:149-153）称并发上限是「已配 failover key 数（the real ceiling on parallel calls）」， 实现缺省回落 SENSENOVA_KEY_VARS.length（=3），而线路池真实条数是 key × 模型 = 12。

后果：多条并发请求可能压在同一 key 的同一模型上，直接打入 429 冷却。 把「key 数」当「线路数」既低估了线路总数，也无法表达「每 key 限流」。

这是全项目最值得学的部分：把「缺陷类」变成「门禁」

作者反复使用同一个手法 —— 每修一个漏挂，就补一条门禁让同类问题未来自动变红，而不是修一次了事。 三个典型例子：

  • test.include 不含 headless/** 而 coverage 含它 → 补 include， 并新增 check-tests-collected.mjs；该门禁判据刻意取自 vitest list --filesOnly 的真实输出，而不是自己解析 include 再匹配 glob（后者要重实现 picomatch 语义，会与 vitest 真实行为分叉）。
  • check-syntax.mjs 不认 .js → 扩到 .js，而不是放宽门禁。
  • release.yml 打 tag 直接 build、不先跑 verify → 加 verify job 并让 build needs: verify。

变异测试：区分 aggregate 与 site 两个口径

口径命令含义
aggregatenpm run mutation每算子至少一处被覆盖 —— 会掩盖位点
sitenpm run mutation:audit每一处位点单独验证

为什么必须区分：aggregate 用 replaceAll 一次改掉某算子的全部位点，「任一处被杀」即报杀死。 项目文档记录过一个实例：snapshot-store.ts 的 aggregate 报 2/2 全杀， 而源码里有 12 个 continue，拆单点后 5 处存活。

这个区分本身就有价值 —— 大多数项目连「变异测试」都不做，更不会质疑自己的口径。

中但 verify 里跑的是最弱档

mutation:quick = --tier=1 --limit=1，每个 tier-1 目标只跑 1 个 aggregate 变异。 它过了不等于「每处位点都有断言」。作者在 SKILL.md 的「三条硬事实」里第一条就写明这一点， 并把全量 site 审计单独放在 CI 的 mutation-full job（35 min 上限）。

这是诚实的自我标注，但如果读者只看「verify 全绿」就以为变异全覆盖，会误判。

5.1 新模块未进变异门禁

低本次新增的 shared/policy-file.ts 与 electron/sandbox/policy-dir.ts 在 mutation-check.mjs 的 TARGETS 里零命中。

该项目自己的铁律写着：「新变异目标要自己登记，否则新代码不进变异门禁」 （.qoder/skills/ox-commander-dev/SKILL.md）。

6. 文档与自洽性

这个项目的文档量远超同类：README 20KB、CHANGELOG 97KB、docs/ 下 10 篇专题报告 （含 113KB 的全栈评审、82KB 的实施全记录）。更有价值的是它自带一份给 agent 用的开发手册： .qoder/skills/ox-commander-dev/（SKILL.md + 两份 references）。

设计亮点：「别信文档，以代码为准」被写成了手册章节

手册里有一节叫「已知不一致」，逐条列出 README/docs 与代码的口径差异，并在不成立时标注「已修」。 这种做法在开源项目里很少见 —— 多数项目选择删掉旧说法，而不是留下审计轨迹。

被记录并修正过的实例： README「审计按天轮转」→ 实际按大小 2 MiB； README「回滚/隔离/报告四档」→ 曾实际只有三种行为； docs 与代码的「930 用例」→ 实际 1151 等。

设计亮点：作者主动推翻自己子代理的结论并留证

docs/2026-09-24-consistency-review.md 开头记录：两只只读子代理调研后，主代理逐条回代码复核， 当场推翻了两条回报 —— 一条是被留档日志污染的用例数， 另一条是「scoped-env.ts 注释与代码自相矛盾」被判定为假缺陷 （两层都叫 allowlist 是措辞陷阱，代码实际让 grants 优先于 denylist，注释与实现一致）。

这正是我本次分析时采用的同一方法（见第 3 节，我实测推翻了子代理的「尾随点绕过」结论）。 说明作者对「AI 报告需要回代码复核」这件事有清醒认识。

低文档与代码的行号锚点会漂移，且手册自己承认

变异门禁的等价白名单在 scripts/mutation-check.mjs 的 EQUIVALENT_SITES 里 以 {file, op, line} 行号锚点登记。在锚点行上方插/删行 → 白名单失配 → site 口径当场红。 手册对此的态度是：处置应是「按新行号校回并重新确认那两层防御仍在」，不是删表项 —— 这个原则是对的。

另一处：src/*.test.ts 里几十个 it("[375] …") 的数字编码的是写下那天的行号， 代码一挪就过期（[375] 那段现在在 orchestrator.ts:432）。 手册明确提醒「按名字读它，别拿它定位」。

把 verifier.ts:286 的正则从「取第一个」改为「取最后一个」，或改用 child.on("close", code) 的真实退出码（后者更彻底，但需要改 runOnce 的返回结构）。

同时补一条回归用例：子进程打印 [exit]0 但真实退出码为 1 → 必须判失败。

P1收紧 H1（basename 冒充） —— 两条可选：

  • 命令为路径形式时，要求它落在可信目录（PATH 内的标准安装目录 / 项目 node_modules/.bin）
  • 或对路径形式的命令做 realpath + 前缀校验，拒绝「项目根内的可执行文件」被当作白名单命令

注意这会碰 command-policy.ts 的变异门禁目标（含等价白名单行号锚点）， 改完要按手册规则校回锚点。

项目自评已指出：「沙箱是全赛道最稀缺的能力……在同类里是头部水平，但对外完全没讲」。 当前 README 里安全边界藏在文档中部，而竞品矩阵显示 12 个同类里 4 个在沙箱维度是 0/6。 这是「已有优势没变成可展示证据」的典型。

P2补齐 M4/M5 的两个「名不副实」

  • maxTokensPerRun：要么改名（如 tokenBudgetHint）以消除「闸门」的暗示， 要么补真正的事前拦截（项目自己也在 CHANGELOG 里把这条列为「留待后续」）
  • maxConcurrency：改成按线路数（key × model）计算，或在 capabilities() 里 明确暴露「这是 key 级并发」的语义

10. 总体评价

做得好的地方（值得其他项目学的）

  1. 把「缺陷类」变成「门禁」 —— 不满足于修一次，而是让同类问题未来自动变红。 这是整个项目最有价值的工程实践，也是它 20 段 verify 的由来。
  2. 对判定口径的自我批判能力 —— 主动区分 aggregate 与 site 两个变异口径， 并公开承认「verify 里跑的是最弱档」。多数项目连变异测试都不做，更不会质疑自己的口径。
  3. 回滚的「正面证据」纪律 —— 把「没有备份」定义为未知而非「新建」， 并留下具体翻车形态（根级 package.json 每轮重修被删一次）。这是数据安全的正确姿态。
  4. 工程诚实度 —— 盲区显式声明而不是假装管住（maxTokensPerRun 软上限、 idleTimeoutMs 被忽略、沙箱不管网络、serve 无鉴权）。「注释的价值高于实现本身」这类判断， 通常只有踩过坑的人写得出来。
  5. 「别信文档，以代码为准」写进手册 —— 并保留「已修 / 未修」的审计轨迹，而不是删掉旧说法。
  6. 对 AI 产出保持复核纪律 —— 一致性评审记录里明确写了子代理回报被当场推翻两处， 包括一个被误判为缺陷的措辞陷阱。
  7. 分离关注点的实现质量 —— serve.ts 把纯路由函数与 socket 部分拆开、 protocol.ts 的 parseSpec 是纯函数并聚合 issues， 协议可离线单测，无需起服务。

需要正视的部分

  1. 当前处于不可交付状态 —— 一处字段声明漏写，导致 20 段门禁只有第 1 段通过。 这本身不严重（半成品），但说明改动过程中的「快档验证」没有跑到位。
  2. 沙箱容易被误读为安全边界 —— 它防误伤、可回滚、可归因，但不防恶意代码。 名字叫「沙箱」，README 有说明，但风险在于使用者跳过说明。
  3. 变异门禁的覆盖有真实缺口 —— 本次新增的 policy.d/ 两个模块零登记； 而项目自己的铁律要求新模块必须登记。
  4. 文档体量已接近维护上限 —— CHANGELOG 97KB + docs/ 累计 300KB+。 新增读者（或新 agent）需要先读手册才能安全改动，因为关键约定散落在代码注释里 （行号锚点、算子字面量污染、zone 三处判据故意不同）。这是高门禁项目的固有成本。

综合判断

这是一个工程素养明显高于平均水准的 43 天个人项目：架构分层清晰、门禁体系罕见地完备、 对自身缺陷的记录坦诚到近乎苛刻。它的核心竞争力不在功能数量，而在「交付一份过了门禁的结果」 这一命题上愿意付出的自证成本 —— 变异测试逐位点审计、动手前跑基线、按 zone 归因重修、 回滚只删有正面证据的文件，这些都不是容易做的选择。

它当前的主要问题只有两类：一是一处未完成的改动让门禁全红（补一行即可）； 二是几处安全判定可以被绕过（命令白名单的 basename 匹配、冒烟结论的正则可伪造）， 其中沙箱的定位限制作者已在 README 声明，但命令白名单那两条属于实现层面的可加固点。

作为对照：这个项目在「沙箱 / 验证闭环 / 变异门禁」三个维度上确实领先于同类的 12–15 个项目（多数在沙箱维度是 0/6），但在「被看见」和「多端可达」上是空白。 技术优势尚未转化成产品势能。
