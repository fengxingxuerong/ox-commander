### 1.2 `buildEscalationSummary` 的两个数字 —— 断言构造错，互换全绿 `[事实]`

`src/prompts.test.ts:76-77` 写的是 `expect(s).toContain("3"); expect(s).toContain("2")`。
而 `shared/prompts.ts:104` 渲染的是 `重修 ${attemptsSoFar} 轮后仍未通过验证（上限 ${maxRepairRounds}）`。

**修复**：数字换成 7/4（避开错误摘要里的数字），断言改成钉住绑定关系的完整片段

**D1 是这轮最重要的发现，也最讽刺**：这个项目最核心的卖点是"zone 互斥下的共享

1589 条用例一条都没发现它，因为它们都在写入与 `begin()` 之间隔了至少一个 tick。

## 8. D1 的修复：为什么是两道措施而不是一道

先量了几种候选方案的成本，再决定：

| 方案 | 实测 | 结论 |
|---|---|---|
| `statSync(p, {bigint:true}).mtimeNs` | mtimeMs 漏 78.7% / mtimeNs 漏 81.7%，**两者都没被区分开** | 否决：换不来精度 |
| 全树内容哈希 | 2000 文件 × 2KB = **236ms/批** | 否决：无条件做太贵 |
| 基线后等 5ms | 漏检 74.7% → **0/150** | 采纳（主） |
| 内容摘要兜底（仅 zone 外） | 接近 0（≈ zone 外文件数） | 采纳（补） |

最终是两道互补：基线拍摄后自旋等一个时钟刻度（`SETTLE_WINDOW_MS = 5`），让基线
时间戳先变旧；两个廉价信号仍撞车时，才对 **zone 外**文件读内容比对摘要。zone 内
留在廉价路径 —— 那不是安全问题，付那个成本不值。

自旋等待有个坑值得记：第一次写成无上限 `while (Date.now() < until)`，结果
`sandbox-journal.test.ts:1866` 的 `vi.useFakeTimers()` 冻结了时钟，**整个测试文件
永久挂起**（我第一次跑就卡了 10 分钟）。现在带迭代上限，冻结时钟下立刻返回 ——
而且冻结时钟本来也产生不了真实的 mtime 撞车，让出等待不损失任何东西。

**怎么找到的**：本来在查另一个假设（XSS），读到页面脚本时看见

有审批在等时，**审批列表排在前面**。

`ul.appendChild` 进去，与「批准 / 拒绝」按钮混成一条列表。

用 jsdom 跑页面**自己的 `<script>`** 复现：

```
<ul> count: 2
  ul[0]  items=["npm run deploy · 批准 拒绝", "log  LIVE-EVENT-FROM-SSE", "done  {...}"]
  ul[1]  items=["log before-page-load"]
"LIVE-EVENT-FROM-SSE" landed in ul[0]
approvals ul now contains 3 li（期望 1）
```

**为什么它重要**：这页存在的唯一理由是「离开工位也能看一眼」。而它恰好
**只在有人在等审批时出错** —— 也就是最需要你看清发生了什么的时候，
事件流却落进了审批列表。且事件越多，审批列表越乱，批准/拒绝越难找。

**修复**：两个列表各自带 class，脚本按 `ul.events` 选取。

**回归测试为什么用 jsdom 而不是断言 HTML 字符串**：bug 在**脚本执行后**的
DOM 里。断言字符串只能证明"class 写对了"，证明不了"脚本按 class 选中了" ——
后者才是缺陷本身。测试在 jsdom 里执行页面脚本并真的 append 一次。

**反向注入**：把选择器改回 `querySelector("ul")` → 该用例转红（29 中 1 红）。

### 17.3 一个被证伪的假设：serve 页的 XSS

我一度以为这里有存储型 XSS，理由：`requestId` 被插进
`onclick="settle('${p.requestId}', true)"` 的 JS 字符串字面量里，
而 `esc()` 只转义 `& < >`，**不转义引号**。注入
`x'); alert(1); //` 确实能逃出字面量：

```html
<button onclick="settle('x'); alert(1); //', true)">批准</button>
```

**但不可达**：`requestId` 由服务端自己铸造（`serve.ts:297`
`a-${seq}-${Date.now().toString(36)}`），引擎无法指定它。其余会进 HTML 的
agent 可控字段（`command` / `args` / log `text` / receipt `headline`）
都过了 `esc()`，且落在**文本上下文**（`<code>` / `<li>` / `<pre>`），
`<` `>` 已足够。

所以结论是**潜在**而非现存：全页唯一的属性 sink 恰好没有可用的引号转义，
将来任何字段被路由进那个按钮（或新增 `title=` / `data-=`）就成真 XSS，
而不会有任何测试变红。**记下来，不改** —— 今天加一个"转义引号但属性里不用"
的死代码，比留着这条明确的记录更糟。

顺带否掉一个更差的修法：我第一版直接把 `maskNonCode` 那类思路搬过来做
"更严格的转义"，结果 SSE 那条路径用 `createTextNode`（本来就安全），
服务端渲染用 `esc()` —— 两条路径本来就不一致，测试却只断言了字符串。

### 20.2 D11：serve 入口的 `--port` 静默回落 —— 一个真缺陷

```
["--port=99999"]    → undefined（静默回落）
["--ports=8080"]    → undefined（静默回落）   ← 拼错的 flag
["--port=8080x"]    → undefined（静默回落）
```

端到端跑一遍：

```

→ OxCommander serve: http://127.0.0.1:58320/ （…）      exit 0
```

**真缺陷**，而且形状和第四轮 `--serve=` 一模一样：不报错、静默用默认值、
exit 0、服务自己看起来一切正常。`serve` 的契约是"我监听在你说的那个端口"，
调用方拿到一个自己没选过的端口，之后每一步都连不上。

已修：给错 → exit 1 + 说清用户实际写的值；**不给**仍然是合法默认。

### 20.3 一个测试基础设施问题（比上面两条更值得记）

补入口级测试时踩到：`npm run verify` 的顺序是
`test` → `build` → `build:headless`，**测试跑在构建之前**。
`vitest.config.mts` 里也没有 `globalSetup`。所以任何"spawn dist 产物"的测试
（在 dist 里存在的前提下）测到的都是**上一次构建的旧二进制**——
源码已经修好，dist 还是旧的，两条用例红。

我一开始以为是修复没生效，查了 mtime 才发现是这个。
处置：测试自己按新鲜度重建（源比产物新才 rebuild），不依赖外层顺序。
**这也意味着这个仓库此前没有任何测试碰过 dist 产物** ——
所以它才一直没被发现。

（补：重建最初塞在每条用例的第一行，全量 `verify` 时 60 个 worker 抢 CPU，
`tsc -b` 超过 vitest 默认 5s 用例超时 → 报 "Test timed out"，症状完全不像
构建问题。真因是**全局一次性动作被放在了每条用例的时限里**。已移进
`beforeAll`，时限独立且给到 120s。）

## 22. 第八轮：把"漏挂 TARGETS"从注释变成门禁

### 22.1 为什么它比看起来更要紧

`mutation-check.mjs` 的 `TARGETS` 表开头就写着"新文件必须显式入表 ——
touched 口径靠这张表映射，**漏挂 = 永远无人审计**"。上一轮我改的三个文件
一个都没在表里，也就是说**前两轮的修复当时没有被任何变异验证覆盖**。

这件事的坏处不在于"少测了三个文件"，而在于：门禁照样报 PASS，
而那个 PASS **对漏挂的文件没有任何含义**。它读起来像"每个算子至少有一处
被断言覆盖"，实际是"我登记的那些文件都覆盖了"。这是最坏的一类门禁失效 ——
**它不报警，它只是撒了一个谎**。

### 22.2 新门禁，以及"为什么不用分支数阈值"

`scripts/check-mutation-targets.mjs`，接进 `verify` 第 10 段之后。

第一版思路是"分支数 > N 就该入表"。**写完就否掉了** —— 那是个启发式，
而启发式有两个问题：一是阈值可以被人为调松来消音，二是它防的是
"这个文件重不重要"，而真正要防的是"**我改了它却忘了登记**"这个动作。
所以直接比对 **git diff × TARGETS**：改了生产文件，就必须登记或显式豁免。

豁免表带失效检查（文件已删或已入表 → FAIL）。理由和 `check-unwired.mjs`
同源：**腐烂的白名单比缺失的白名单更糟** —— 缺失的白名单至少诚实，
而失效条目会被下一个人当成"已经评审过"的证据。

反向注入 4/4。**注入脚本自己也翻车了一次**：第一次跑报 3/4，
看起来像门禁有洞。查下来是**注入脚本的字面量用了 `\n`，而仓库那个文件是 CRLF** ——
`String.replace` 静默不匹配，于是什么都没注入，门禁"通过"。
把注入改成正则 `\r?\n` 并**在没匹配上时直接抛错**之后才是真正的 4/4。
（教训：**注入脚本必须自己报告"没注入到"**，否则它测的是一个没被改动的世界。）

### 22.3 它当场回本

第一次跑就查出一份未登记的 `headless/receipt-verify-main.ts` ——
131 行，未入表文件里分支最多的一个，而**它的退出码就是 CI 的判定**。

入表 → 逐位点 → **3 处存活**：

- **124 行 `=== !==`**：把 `unsigned` 也报成 `tampered`。
  `auditReceipt` 的五档在 `delivery-receipt.test.ts` 里测得很细，
  但 **verdict → 退出码这张映射表一处断言都没有**。而文件头明写
  "每一档对应一个**不同的处置**，刻意不并档"，其中"只有 verified 可采信"。
  这一处断了，下游把"没盖章"读成"被改过"，处置从"补盖章"变成"查差异来源"，
  **方向直接错了**，而且没有任何测试会红。
- **95 行的 `&&` / `!==`**：指纹不符时**不复跑**的那道守卫。
  这是安全相关的一道闸：拿假凭据复跑出来的"矛盾"是伪证的产物。

补完 **8/8**。五档全部真进程端到端验证（0/2/3/4/5），外加一条
"五档互不重叠"的机器检查 —— 把文件头那句"不许并档"变成可执行断言。

写这组用例时我又踩了一个坑：用 `node -e "process.exit(0)"` 当复跑命令，
实测两档都拿到 exit 2，看着像"复跑与凭据矛盾"，**其实是被 `CommandPolicy`
拒了内联求值**（stderr 明确写了）。也就是说那两条断言**测的根本不是
我要测的东西**，却差一点就绿了 —— 如果我当时只写"exit 2 = 矛盾"这一条，
就会完全测不到"exit 0 = 复现"这个最重要的一档。
改用真脚本文件（沙箱允许的形状）之后才对。

### 22.4 全量 site 复审：64 个目标全 100%

新门禁上线后跑了一次全量逐位点审计（`--mode=site --limit=9999`），
**64 个目标 / 1312 处位点，全部 100%，EXIT 0**。

顺带一个操作纪律：`mutation-check` 运行期间**不要对源码跑任何别的门禁**。
我在全量 site 审计跑着的时候并发跑了一次 `check:mutation-targets`，
拿到 EXIT=-1 且无输出 —— 因为那时源码正被变异器改写。
这不是产品缺陷，是工具使用纪律，已记在文档里。

### 22.5 横向比对：两个宿主各自都过了变异门禁，但其中一个缺了一整类能力

审计清单清空之后换维度。选的是这个：

> `electron/engine` 与 `headless/serve.ts` 各自都通过了变异门禁，
> 但**"两个实现都测过"不等于"两者语义一致"** —— 而这正是重复实现的典型裂缝。

先比了 pause：两边**一致**，而且 serve 状态页那句"当前任务跑完就停"经实测是
准确的（`gate()` 只在派发前检查，正在跑的批次不会被掐断）。顺手确认了
`state.paused` 是"请求已受理"而非"引擎已停"——但两处措辞都把这个区别说清了，
所以不是缺陷。

**真正不一样的是 cancel。** 实测：

```
state.status = "idle"          ← 引擎还没挂上，pause/resume 都答 409
等待审批 = ["git"]
POST /pause  → 409   POST /resume → 409   POST /cancel → 404
再 POST /run → 409 "已经有一个 run 在跑"
```

坏处不是"少一个按钮"，而是一个**卡死**：等审批的 run 永远出不来，后续 run 全被
busy 挡住，整个服务只剩"有人去批准那条命令"这一条出路。桌面形态点一下取消就解了
——`orchestration:cancel` 里的 `cancel` / `abortAllEscalations` / `abortAllApprovals`
**三件事并列**。

### 22.6 修的时候，我自己写了一个 bug 又修掉

修的第一版把"放掉挂着的审批"只放在**没有引擎**那条路上，理由是"卡在审批里说明
引擎还没挂上"。**那个前提是错的**：`onEngine` 在规划前就被调用（`run-spec.ts:312`），
审批发生在更后面的执行阶段 —— 于是引擎早就挂上了、走的正是**另一条**分支、
审批一个都没放，**死锁原封不动**。

是反向注入抓到的：把"引擎分支也放审批"改成 `const released = 0`，门禁全绿。
现在两条路径都调 `releaseAllApprovals()`。

同一个坑还有另外两面：

- **判据必须用 `busy` 而不是 `engine`**。第一版按 engine 判，结果从来没跑过
  任何 run 时它恒为 undefined，`/cancel` 报 200 "已中止"而它什么都没中止。
  实测三态：从来没跑过 → 409；跑完一个 run 之后 → 409；run 在跑而引擎未挂上 → 200。
- **引擎不支持中止时答 501**，不假装成功（`EngineControl.cancel` 是可选的）。

措辞也跟着分开：暂停说"当前任务跑完就停"，中止说"**已请求中止**：正在跑的任务
不会被掐断"。`已中止` 三个字要等引擎真在检查点停下来才配得上。

反向注入 6/6。`serve.ts` 变异 **55/55**（原 47/47）。

### 22.7 注入脚本本身翻车了两次，值得单独记

第一版注入脚本报 3/6，看着像三条断言没咬住。查下来是**正则没锚定位置** ——
`cancelWithoutEngine` 里有一模一样的两行，不加锚就改到那一份去了，
"注入成功"而测的是另一处代码。加锚之后 5/6。

第二次（⑤）是真的等价变异：`if (!busy && !engine)` 的 `&& → ||`。
穷举赋值点后确认等价 —— 唯一能区分两种写法的时刻是 `B=1 ∧ E=0`，
而那一刻两种写法**都**落到 `if (!engine)` 那支，只是快慢差别不是行为差别。
进 `EQUIVALENT_SITES` 并附上完整推理与"将来若改变 busy/engine 的赋值顺序
这个等价就不再成立"的复核条件。

（第五次事故：注入脚本**改了文件却报告门禁全绿**。现在它会在
`replace` 结果与原文相同时直接判失败 —— 因为那种"注入了但等于没注入"
会把一句谎话包装成一次通过。）

### 22.8 SettingsPage：补注释，但不是凑密度

体检报告说它注释密度 8%（全项目大文件最低）。实测 2.3%（口径不同，
我的统计是"整行注释"）。我没有为了拉数字去给自解释的代码加注释 ——
`movePoolMember`、`togglePoolMember` 这些一看就懂的函数不需要注释。

补的是**读代码第一反应一定猜错**的两处，都在密钥相关路径上：

- `clearKey`：**删除 = 用空值再存一次**，没有独立的 delete 调用。
  第一反应一定是"漏了 delete"。注释补上为什么这样设计（删除与写入共用
  一条路径，就不存在绕过审计直接抹掉的可能）。
- `handleSaveKeys`：**过滤空串是刻意的** —— 清空输入框**不等于**删除密钥，
  否则用户只是把光标删干净了就丢了盘上的凭据，那是个不可逆的意外。

密度 2.3% → 5.4%。判断标准是"这条注释能不能防止一次误改"，
不是"这个函数有没有注释"。

### 22.9 横向比对的第二跳：下游缺口也是缺口

上面那个死锁修完之后顺手想到：**`ox_control` 的 action 枚举只有 `pause`/`resume`**。
也就是说 serve 有了 `/cancel`，**MCP 客户端仍然中止不了** —— 而 pause 在卡住时
恰恰不生效（引擎还没挂上）。等于"用 MCP 驱动的人永远解不开那个死锁"，
只是从"谁都没法解"变成"只有拿 curl 的人能解"。

同一个横向比对顺手还发现 `ox_status` 只读 `s.paused`，中止后客户端看到的是
"状态 running"，**完全看不出有人点了中止**。而中止恰恰是最需要被看见的状态
（run 即将结束、等待中的审批被 fail-closed 放掉了）。

两处都补了，并守住 schema 与实现一致：**枚举里没有 `cancel` 而实现认它，
客户端就永远发现不了这个能力**（那条断言一开始还真抓到了不一致 ——
答复文本写"跑完后退出"、工具描述写"不会被掐断"，两句对同一件事的描述不一致）。

`mcp.ts` 变异 71 → **77/77**，六个新位点全部一次杀死。

**这一跳的收获印证了横向比对的价值**：上一跳发现的是"serve 缺一整类能力"，
这一跳发现的是"补上之后下游还没跟上"。前者的根因是重复实现，
后者的根因是**改一处要记得改三处** —— 而后者只能靠横向看，不能靠改那一处时顺手。

### 22.10 运行时观察：真起一次交付，抓到三处自相矛盾

前两轮横向比对的收获是同一件事的两面：**每个对外呈现的词都得对得上引擎的真实语义**。
但横向比对是"对着两处代码看"，看不出**同一次 run 里三个说法互相打脸**。
所以这轮不看代码 —— 起一个假大脑 + 假桥（与 `offline-e2e-it.mjs` 同形），
让 `serve-main` 真跑一次完整交付，同时从四个面采样：
SSE 事件流 / `/state` / 状态页 HTML / MCP。

第一次跑还撞出我自己诊断脚本的两个错，都记在这里：

- 任务 schema 我写成四项（`taskId`/`description`/`zone[]`/`deps`），真实契约是
  **六项**（`id`/`title`/`description`/`zone`/`dependencies`/`suggestedRole`），
  于是第一轮 run 在 93ms 就 `schema validation failed` —— 一份失败的凭据都没有。
- 我等 `/state` 的 `status` 变化，但 `status` 只在 **`hello`** 事件里才变。

跑通之后，观察到的是这样的（真实输出）：

```
verification 事件 ×2，两次都 passed=true，results 里 ok:true exitCode:0
log ×2：「警告：存在失败的开发任务，即使构建通过也不允许交付。」
escalation ×2：「重修 2 轮后仍未通过验证（上限 1）」+ 摘要 "no agent available"
receipt：checks[0].ok=true，同时 unverifiedReason="重修 1 轮后验证仍未通过"
error："verification still failing after 1 repair rounds"
```

死因是 `no-agent`（调度器没匹配到执行者）。这种死因有个**必然性**：
项目文件压根没人动，基线本来就是绿的，于是验证**必然**全绿。
而三处表述都说"验证没通过"：

1. `orchestrator.ts` exhausted 分支的 `unverifiedReason`；
2. `VerificationExhaustedError` 的 message（会进宿主日志与 SSE 的 error 事件）；
3. `buildEscalationSummary` 的第一行 —— **紧跟着下一行就是 "no agent available"**。

第 3 条最有害：用户正要照着"跳过 / 重派 / 终止"三选一做决定，
他会以为是代码坏了去选"重派"，于是又烧一整轮。

引擎在 `orchestrator.ts:701` 自己就清楚这件事（它专门打了一行日志说"存在失败的
开发任务，即使构建通过也不允许交付"）—— 说明它**知道**两者不同，
只是没把这份知识带进凭据、错误和弹窗。**知道的和说出来的之间有一条缝**，
这一轮就是照着那条缝修的。

三处都按 `report.passed` 分成两种说法；**class 名与退出码不动**（协议的一部分），
只把话说准，另加 `verificationFailed` 标志位供宿主分辨。
修完用同一个脚本重跑，三处都变了：

```
escalation：重修 2 轮后仍未完成（上限 1）。验证命令是通过的 —— 卡住的是任务本身没做出来。
receipt：重修 1 轮后仍有 1 个任务未能完成（验证命令全部通过，但产物并未做出来）
error：1 repair rounds spent; verification passed but tasks did not complete
```

反向注入 5/5。其中⑤（把 `verificationPassed: report.passed` 改成 `false`）
第一版**没被抓住**—— 因为 `prompts.test.ts` 里那几条是直接调
`buildEscalationSummary` 并自己传参的，它们管得住**措辞**，管不住**连线**。
补了一条端到端断言才咬住。这类"参数写了但没人传"的漏洞值得单独记一笔。

还顺手改掉一条**一直绿、但绿得没有意义**的旧断言：
`orchestrator.test.ts:2178` 的 `toContain("验证仍未通过")`，而它配的引擎验证是
**通过**的 —— 它测的是一个不存在的场景。

变异：`orchestrator.ts` **51/51** · `shared/prompts.ts` 1→**2/2**。

### 22.11 这一轮的方法论：为什么静态审计查不到这类问题

门禁、变异、断言都能回答"这段代码的行为是不是被我钉住了"。
它们**回答不了**"这几个互相独立的表达，在同一次运行里说的是不是同一件事"——
因为矛盾不在任何一段代码里，而在**它们的关系**里。

反过来说，一旦把矛盾写成断言（"全绿时不得说验证未通过"、"说了验证通过就
不得说未通过验证"），它就变成了一个普通的可测不变量，门禁管得住。
**前提是先真跑一次、看见矛盾。**

### 22.12 凭据自洽性审计：换个采样面，又抓到一处

第十轮盯的是编排期（凭据/错误/升级弹窗）。这轮把采样面移到**凭据内部**：
`counts` 的六个数、`tasks[]`、`checks[]`、`rounds` 与 `headline` 那一句，
讲不讲同一个故事。写成 13 条可从一份凭据算出的不变量（不依赖再跑一遍）：

```
I1  counts.total == tasks.length
I2  done+failed+skipped+pending == total
I3  counts.checksFailed == checks 里 !ok 的条数
I4  counts.preexisting == checks 里 preexisting 的条数
I5  counts.conflicts == conflicts.length
I6  headline 的 "done/total" == counts.done / counts.total
I7  headline 的"跳过 N 个" == counts.skipped
I8  headline 的"重修 N 轮" == rounds
I9  outcome=blocked 时必须说得出原因（failed/pending/checksFailed 至少一项 >0）
I10 outcome=delivered 时 done+skipped == total
I11 verified=false 时不得说"条验证命令通过"
I12 checks 有红项时不得说"条验证命令通过"
I13 兜底话术「仍有任务未完成」不许出现在真实形状里
```

起六种形状的真 run（不是构造对象）逐个核对，**I9/I13 当场破**：

```
counts = {"total":2,"done":2,"failed":0,"pending":0,"checksFailed":1,...}
headline = "未交付：2/2 个任务完成，仍有任务未完成，重修 1 轮。"
                            ^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^
                            任务全做出来了     却说还有任务没做完
```

根因：`receiptHeadlineFor` 的 blocked 分���只从**任务账**里找原因
（`failed`/`pending`），从不看 `checksFailed`。这个形状下两个数都是 0，
兜底话术顶了上来——而它跟同一句的前半截直接打架。

**这不是边角。** `checksFailed>0 && failed==0 && pending==0` 是**最普通的一种红**：
代码写完了，构建/测试没过。而这条分支此前**一条断言都没有**——
`grep「仍有任务未完成」` 与 `grep「条验证命令通过」` 都是零命中。

修法：结论优先按验证说。理由不是措辞偏好，而是**读者要据此决定下一步**——
"东西做了但门禁没过"要去改代码，"东西没做出来"要去改配置或加 agent，
合成一句话就等于把决策依据拿走了。

### 22.13 审计脚本自己骗了我两次

第一次：桥是**在 spec 的 `agents[]` 里声明的**，不是环境变量。我第一版写成
`OX_AGENT_BRIDGE_URL`，于是没有任何 agent 匹配角色，**六种场景跑出六份
一模一样的 blocked 凭据**，而脚本报"全部通过"。

这个最阴险的地方在于：它不是报错，是**造出一片虚假的绿色**。
六个场景结果全等，恰恰是"场景参数根本没起作用"的信号 —— 我当时没看这个。

第二次：想造"没有可用 agent"的形状，我写了 `agents: []`。那是 **spec 非法**，
服务直接 400，run 压根没开始（`status: idle`、零事件）。而"没跑起来"和
"跑出了预期形状"，在只数场景时长得一模一样。得声明一个**角色对不上**的 agent
（`roles: ["docs-writer"]` 配 backend-dev 的任务）才造得出那个形状。

**教训**：观察脚本和被测系统一样需要被质疑。"六个场景结果一致"这种信号
不该放过 —— 它比任何 FAIL 都更像"你测的根本不是你以为的东西"。

### 22.14 一条我以为的等价重写，其实是缺陷

⑤ 反注入把 `checks.length` 换成 `checks.filter(ok).length`，我先判定这是
等价重写（`delivered && verified` 分支上 checks 按设计全绿），
于是打算把它记成"预期存活"。

跑完发现**它死了**——因为 `headline 里的每个数字都必须能在 counts 里找到`
那条断言顺手咬住了。教训：**"等价"是结论，不是可以先下的判断**。
我给注入脚本写了个注释说"预期存活"，而那个注释是我编的理由，不是观察。
观察优先于理由 —— 这条在第九轮也栽过一次（`state.paused` 那次）。

反向注入 5/5。`shared/delivery-receipt.ts` 变异 **43/43**。

### 22.15 方法论：多面采样的产出，比新增门禁高

第十、十一轮都只是"起一次真 run，看几个面各自说了什么"，没有新增任何门禁机制，
但各抓到一处真实缺陷。而这两处——

- 凭据说"验证未通过"而它自己的 `checks` 全绿；
- 凭据说"2/2 完成"紧接着"仍有任务未完成"——

**都是任何现有门禁结构上不可能发现的**：它们不是"某个函数被调用了几次"的问题，
而是"几个各自正确的表达放在一起不成立"。门禁的形态（逐点变异 + 断言）
天然擅长前者，不擅长后者。

反过来，一旦把它们写成不变量断言，它们就变成了普通可测的东西 ——
第十轮的三处措辞、这轮的 13 条，都已经进了变异门禁，位点全杀。

### 22.16 采样面 ③：重修轮的账 —— 「重修 3 轮（上限 2）」

前两轮采样都只跑了 0–1 轮重修。而"轮次相关的数字"恰恰是最容易互相对不上的地方。
这轮造一个**前 K 次失败、第 K+1 次成功**的 agent，让引擎真的走满多轮，
把 `tasks[].attempts` / `rounds` / escalation 那句 / usage 四处排在一起对。

usage 那条线**查完是好的**：`measuredCalls ≤ calls` 由 `UsageMeter.record()`
结构保证（未上报用量时提前 return，不进 `measured`），所以 `formatReceiptLine`
的 `calls - measuredCalls` 不可能为负。这条记下来是因为"查过"和"没查"要分开记。

轮次那条线当场破：

```
escalation：任务「唯一任务」重修 3 轮后仍未完成（上限 2）
                 ^^^^^^^^                     ^^^^^^
                 重修轮数                      上限也是重修轮数
tasks[].attempts = 3（= 派发总次数，含首次）
rounds = 2
```

**两个数字量纲不同**：`attemptsSoFar` 是派发总次数（含首次），
`maxRepairRounds` 是重修轮数（不含首次）。并排印必然差 1 ——
于是印出"重修 3 轮（上限 2）"，一句不可能成立的话。

而用户正是照这两个数判断"还剩没有机会再试一次"。

改成同一口径，并顺手修掉一个边界：

```
已尝试 3 次（首次 + 重修 2 轮）（还能再重修 0 轮）   ← 第一版还这么印
已尝试 3 次（首次 + 重修 2 轮）（已达重修上限 2）   ← 修好
```

**"还能再重修 0 轮"是废话**：轮数用尽时该说"已达上限"。
这个边界是我**写完断言之后、被断言逼出来的** —— 我先写的实现判据是 `>`，
断言要求 `>=`，红了才知道边界判错了。第十一轮记过"观察优先于理由"，
这条是它的正面例子：**先写断言，它会告诉你实现错在哪**。

### 22.17 为什么这条在旧测试里永远看不见

`attempts=1, maxRounds=0` → 旧文案印出"重修 1 轮（上限 0）"。
读着别扭，但**不含"超过上限"的荒谬**——因为 1 > 0 看起来只是"超了一点点"。
要印出"重修 3 轮（上限 2）"这种一眼就假的，得 `maxRounds ≥ 2`，
而**所有现成的重修测试用的都是 `maxRounds: 0`**（一轮都不重修，
直接断言抛错）。所以这条分支**从来没被多轮跑过**。

这是个结构性盲区：**"上限 = 0"的测试会把"上限 = 2"的缺陷完全遮住**。
现在补的是穷举：`attempts` 1–8 × `max` {0,1,2,4}，32 组全过。

反向注入 5/5。`shared/prompts.ts` 变异 **2/2**。

### 22.18 观察脚本第三次自骗（这轮）

第一版 agent 只改门禁脚本、不改产物，于是**即使门禁绿了任务本身也没做完** ——
五个场景全跑成 blocked，看着像"轮次参数不起作用"。
第二版产物写了，但标记文件放在**项目根**（zone 声明是 `src`），
于是每次成功都被判**越权**、`revert-batch` 把它删掉 —— 又回到全 blocked。

两次都是"我以为在控制某个变量，实际上控制的是另一个"。
第三次才跑出真正的形状（`attempts = rounds + 1` 在所有 delivered 场景成立）。

**三次都在同一个方向上出错：我搭的脚手架比被测系统更值得怀疑。**

### 22.19 一条我写错的不变量

"说了『仍未完成』就不该同时说『验证命令是通过的』" —— 我第一版这么写，
然后一条**本来就正确**的输出被判红。因为"仍未完成"说的是"东西没做出来"，
与"验证是过的"**本来就不冲突**，两者必须并存。

写不变量时容易犯的错：**把"相关"当成"矛盾"**。
真正的矛盾只有一对：`仍未通过验证` × `验证命令是通过的`。
现在断言写成"两种说法恰好出现一种"，而不是"某些组合不许出现" ——
后者容易在排除项上出错，前者直接钉住互斥。

### 22.20 采样面 ④：断点续跑 —— 静态推理说的缺陷，被运行观察推翻了

上一轮修的是"重修 3 轮（上限 2）"那个量纲错配。这轮盯它的上游：
**`attempts` 跨 run 到底接不接着算**。真跑多轮之前，先把静态推理做完：

| 位置 | 动作 |
|---|---|
| `orchestrator.ts:635` | `attempts.set(t.id, ... + 1)` —— **派发前** |
| `orchestrator.ts:691` | `save()` —— **批次跑完之后** |
| `orchestrator.ts:373` | 取消路径只补 `onTaskStatus`，**不调 save()** |

三条合起来是一份自洽的"缺陷报告"：批次跑到一半被中止 ⇒ 那次派发从未落盘 ⇒
恢复后 `attempts` 从头算，**烧掉的预算没人记得**。我第一版就是这么判的，
连注释和修复方案（加 save）都写好了。

**真跑一次（假桥挂住 + `POST /cancel` + 直接读 journal 文件）推翻了它**：

```
派发中：journal = {"attempts": {},          "round": 0, "allDone": []}
取消后：journal = {"attempts": {"slow": 1}, "round": 0, "allDone": []}
恢复后：凭据 tasks[].attempts = 2   ·   真实派发 = 2 次
```

`attempts` 与真实派发次数**一致**。原因在 `cancel()`（:220）：它不只设标志位，
还调 `abortInFlight()`，让在跑的批次**以 cancelled 收场而不是悬着** ——
于是控制流照常走到 :691，`save()` 照常落盘。

**所以那条 `save()` 是承重的，不是冗余。** 补两条断言钉住它：

- 取消后批次收场时 `journal.attempts` 记着这次派发（**少记** ⇒ 预算被遗忘）；
- 计划快照里 `attempts` **是空的**（**多记更糟** —— 会让上限判断偏松，
  用户以为自己还有预算）。这条是特意配的**反面**风险：修"少记"很容易顺手
  造成"多记"，而后者不会报错，只会让恢复后的运行悄悄放宽上限。

反向注入 2/2：删掉 :691 的 `save` → 被"最终快照含全部完成状态"抓住；
给计划快照预写派发数 → 被"计划快照里 attempts 是空的"抓住。

### 22.21 这一轮最值钱的产出，是一个**被推翻的结论**

前十三轮每轮至少抓到一处缺陷。这轮抓到零处。

但它不是白跑的：**我差点在一条**看起来**充分的静态推理上加 save()** ——
而那条推理的每一环（`:635` 在派发前、`:691` 在批次后、取消路径不 save）
**都能在代码里指出来**，三条单看全对，合起来是错的。缺的那一环是
`abortInFlight` 的语义，而那个语义**只能从运行时行为看出来**。

这跟十二、十三轮"审计脚本自己骗我"是同一个教训的**另一面**：
脚手架会骗你，**静态推理也会**。两者的共同点是——
**都得靠"真跑一次 + 看落盘的真实字节"来裁决。**

也正因如此，这轮的产出形式是**断言**而不是**修复**：
一条承重但看起来冗余的行为，如果没有断言，下一个改 `abortInFlight` 的人
不会知道自己在动什么。而"加个 save 更保险"恰恰是最自然的下一步。

### 22.22 注入脚本自己栽了两次，且两次都往"假阳性"方向

**第一次：判据方向搞反。** 反向注入的判据是"测试必须红"，
我写成 `PASS = 测试红`，然后打印时又把它当 FAIL 显示 ——
于是**断言明明咬住了，我报了 1/2**。这跟第十二轮"把不变量写反"同源：
**判据的方向比判据的内容更容易出错**，因为内容可以验证，方向不能。

**第二次：CRLF。** `orchestrator.ts` 是 CRLF，正则里写 `\n` ⇒ 永远不匹配。
我的脚本有 `replace 空转 ⇒ FAIL` 的保护，所以报了"没匹配上"，
但我一度把上一轮的**残留输出**当成了这次的结果，差点得出
"断言没咬住"的结论。第九轮记过这个坑，**隔了几轮又踩了一次**。

两次都往"假阳性"方向偏 —— 也就是**偏向多修**。
工具在这种时候应该让人停下，而不是让人相信结论。

### 22.23 采样面 ⑤：conflict 账 —— 两条账都对，只有 headline 漏了

第十五轮验两件事（上一轮建议的一组）：**恢复不重跑已完成任务**（第十四轮结论
的反面）与 **conflict 链**。

**第一件是好的**：journal 里 `allDone: ["A","B"]` 时，第二趟真实派发 `[]`。
现有测试已用构造对象断言过 `dispatched`，这轮确认它在真实 run 里同样成立。

**第二件的两条账也都是对的**（两种仲裁模式各跑一次，agent 改 zone 外的
`package.json` 造越权）：

```
counts.conflicts=1   conflicts.length=1
conflicts=[{"kind":"unauthorized-write","paths":["package.json"],"remedy":"revert"}]
```

**但 headline 整句里没有它**：

```
未交付：0/2 个任务完成，1 个失败、1 个未启动。改动已留在工作区，未通过门禁
```

`conflictPart` 只挂在 `delivered` 那条尾巴上，`blocked` 那条从来不带它。

所以现象很典型：**两份结构化账都对**（`counts.conflicts`、`conflicts[]`），
**只有给人读的那一句漏了**。而那句恰恰是绝大多数人唯一会看的。

这不是措辞瑕疵，是**语义降级**：一次 `unauthorized-write` 在 headline 上
与一次普通测试失败**完全无法区分**。读者据此去看测试日志，
而真正发生的是"智能体试图改 zone 外的文件"——这是安全事件。

修后（真实 run 实测）：

```
未交付：0/2 个任务完成，1 个失败、1 个未启动；发生 1 次越权并已处置。改动已留在工作区，未通过门禁
```

### 22.24 断言先发现了我的第三个出口

我按"blocked 与 delivered 都要说越权"去改，只改了两处就以为齐了。
然后我**按出口枚举**写了断言（blocked / delivered / 未验证交付 / 无越权 / 次数一致），
第一条就红了：

```
× 未验证交付那条出口也不许吞掉越权
AssertionError: expected '已交付但**未经构建/测试验证**：…' to contain '1 次越权'
```

`已交付但未经构建/测试验证` 是**第三条出口**，与 blocked 是同一个疏漏的另一个面 ——
而我改的时候只想着两个outcome，忘了 `verified` 还会分叉。

这是十二轮那条经验（先写断言，它会告诉你实现错在哪）的第二次生效。
区别在于：十二轮是**边界判据**（`>` vs `>=`），这轮是**漏了一个分支**。
两者共同点是——**我心里的"全部"比代码里的"全部"小**，
所以只有枚举出来的才算数。

### 22.26 门禁自己的一次假阴性：机器负载把两条用例拖死了

第十五轮的 `npm run verify` 跑了 **42 分 01 秒**（平时 ~17 分），**EXIT 1**。
两条用例挂了，而且挂法很奇怪——**各自耗时 2485 秒**：

```
× loads settings, lists pool providers and key rows with security notice   2484675ms
× 五档互不重叠：每个退出码只由自己那一档产生                                2486736ms
```

单独重跑，两条都是**毫秒级**通过：

```
npx vitest run src/headless-entries.test.ts -t "五档互不重叠"
  ✓ 717ms
npx vitest run src/ui.test.tsx
  Tests  53 passed (53)   Duration 2.61s
```

两个失败的原因分别是：

- UI 那条：`Error: Test timed out in 5000ms` —— 它的默认超时是 5 秒，
  而那一次它等了 2485 秒才被判超时（说明进程整个被拖住，不是断言慢）。
- 退出码那条更有意思：期望 `[0,2,3,4,5]`，实得 `[2,3,4,5,null]`。
  **`null` 是子进程被信号杀掉**（`spawnSync` 的 `status` 为 null 时）——
  那 5 次复跑里有一次压根没跑起来，于是"第 0 档"的码是 `null`。

两个文件**都不在本轮的改动范围**里（`git status` 里没有 `src/ui.test.tsx`
与 `src/headless-entries.test.ts`），且都是纯 CPU/进程密集型。

**结论：这是机器负载造成的假阴性，不是缺陷。**

但它暴露了门禁的一个真实缺口，值得记下来：

> **`npm run verify` 没有"整体变慢 ⇒ 可能是环境问题"的判断。**
> 平时 17 分钟、这次 42 分钟，**这个 2.5 倍的信号就摆在输出第一行**，
> 但没人会去读它 —— 输出被 `Tee-Object | Out-Null` 吞掉了。

复现时的正确处置顺序（本轮实际走的）：

1. 先看**耗时**，不看通过与否 —— `2485s` 对 `0.7s` 是决定性信号；
2. 单独重跑那两条（隔离 = 排除并发/负载变量）；
3. `git status` 确认失败文件**不在**本轮改动里；
4. 以上三条都成立，才判"环境问题"；任何一条不成立，回去查代码。

第 3 步最容易被跳过 —— 人的默认假设是"我刚改的东西坏了"，
而这次恰恰是**没改的东西坏了**。

### 22.27 采样面 ⑥：分流 —— 一个只喂给"入参"的展开

顺着十五轮那族往下查：**分类对了但对外表述丢了**的下一个面。

真跑两种形状（一直失败 / 第一次失败后成功），拿到凭据第一眼就中：

```
tasks[0] = {"id":"A","status":"failed","attempts":2,
            "agentId":"c-bridge","durationMs":89,"errorClass":"timeout"}
                                  ↑ 没有 outcomeOk

tasks[0] = {"id":"A","status":"done","attempts":2,
            "agentId":"c-bridge","durationMs":67}
                                  ↑ 也没有
```

`status` 说了"失败"/"成功"，但**没说这次派发本身成没成**。

根因是 `orchestrator.ts:459`：

```ts
status: receiptTaskStatus({
  skipped: …, done: …,
  ...(outcome ? { outcomeOk: outcome.ok } : {}),   // ← 展开进了「入参」
}),
attempts: …,
```

这个展开只参与了 `status` 的计算，**从没进过 `tasks[]`**。
而 `ReceiptTask` 里**连 `outcomeOk` 字段都没有**（它只作为
`receiptTaskStatus` 的入参类型存在），所以 TypeScript **静默丢弃**，不报错。

那行注释写着"没有派发结果时不给 `outcomeOk`：那与'派发过且成功'是两种事实"——
**听起来是承诺，实际是从没兑现过的承诺**。

### 22.28 为什么这个错配从任何一侧都发现不了

三道防线**同时失效**，这才是它活到今天的原因：

| 防线 | 为什么没拦住 |
|---|---|
| TypeScript | `ReceiptTask` 没这个字段 ⇒ **静默丢弃**，不报 excess property |
| 现有单测 | 都只 `toMatchObject([…])` 断言 `status`/`agentId` ⇒ **没断言过任何"该出现/不该出现的键"** |
| 变异门禁 | 位点是"某行有没有被调用"⇒ 这行**一直在被调用**（喂给 status 用了）⇒ **活着** |

`grep outcomeOk` 全仓 **6 处命中、零消费侧** —— 没有任何一侧会因为它消失而变红。

**这三条合起来是一条通用教训**：一个字段若**只有生产者、没有消费者**，
那么它"存在不存在"这件事就没人负责。补上它之前，先确认**谁会读它**。

### 22.29 为什么 `outcomeOk` 值得补，而不是删了拉平

`status` 是四态归并的结果，**它丢掉了来路**：

- `done` 可能来自"这次派发成功"，也可能来自**恢复的 `allDone`**；
- `skipped` 是人的决定，与派发结果无关；
- 只有 `failed` 才一定意味着"这次派发失败了"。

所以拿到凭据的人**无法区分**"这次跑成的"与"上一轮跑成的、这次只是恢复"——
而这两者的排查路径完全不同（前者看 agent 日志，后者看 journal）。

删掉它、拉平到 `status`，等于让这个信息**彻底消失**；
留着它，成本是一个可选字段。

### 22.30 反注入当场暴露的第二个缺口

④ 把 `attempts` 写死 0（模拟"计数与派发结果脱钩"）——**测试全绿**。

查下去发现：凭据里的 `tasks[].attempts` **没有任何直接断言**。
现有 4 处 `attempts` 断言**全在 journal 快照上**（`RunSnapshot.attempts`），
**管不到凭据**。同一个概念的两个出口，一个被钉住了、另一个没有。

这不是本轮的缺陷（本轮没改 `attempts` 的算法），是**注入帮我发现的**——
这正是反向注入的额外价值：它不只验"我修的东西被守住了"，
还会顺手撞见**相邻位置没被守住**的地方。

补上 `expect(t.attempts).toBe(1)` 后，④ 也被咬住。反向注入 **4/4**。
`electron/engine/orchestrator.ts` **51/51**。

### 22.31 观察脚本第四次自骗，而且这次错得最有意思

第一版把 `lastError` 挂在 **POST `/v1/runs`** 的返回上，于是两次都判成功 ——
"失败"场景**根本没跑到**，而输出是"delivered + D3 不通过"，看着像个真缺陷。

真实契约在 `http-bridge.ts:326`：`status` 与 `lastError` 是在**轮询响应**
（`GET /v1/runs/:id/events`）上判定的，POST 只负责发车。

**为什么这次特别值得记**：错误的脚手架**制造了一个方向相反的假信号**。
前三次（十一、十二、十三轮）都是"所有场景一模一样"—— 那是**假绿色**，
容易识破。这次是"跑出了一个看起来很有说服力的真缺陷"——
如果我顺手把 `outcomeOk` 当成"本来就该有"去补字段，而不去查它为什么一直缺，
就会在一个**错误的问题**上写一个**看似正确的修复**。

**前三次的教训是"警惕全绿"，这一次的教训是"警惕红得太合理"。**

### 22.40 真正的缺陷：标签并档，且并的是最该分开的两端

`STATUS_LABEL` 只有四个键，于是 `done(passed=false)` 与 `error`
共用 `failed` 一个标签，印成 `未交付 / 出错`。

真实 run 的第一种形状（**最普通的一种红**）：

```
status=failed  outcome=blocked  rounds=1   tasks 1/1 完成，仅门禁红
<title>OxCommander · 未交付 / 出错</title>
```

**两个方向的错都在这里**：

1. 跑完了却被说成"出错" ⇒ 读者去找**崩溃日志**，而实际上一切正常跑完、
   该看的是验证输出；
2. 真崩时也只印这句 ⇒ **崩了这件事被藏了起来**，两边看不出差别。

第 2 条比第 1 条更严重：它不是"误导"，是**信息丢失** ——
最需要被看见的那种失败，恰恰被合并掉了。

判据取**凭据存不存在**：有凭据 = 引擎走完了正常收尾流程
（`receipt` 事件先于终态到达），无凭据 = 崩在中途。
凭据本身就是判据，不需要额外的状态位。

修后（两种结局都真跑过）：

```
未交付（已跑完，门禁未过）      ← done(passed=false)
```

### 22.47 命中的那处：三句互相矛盾的话

`buildResult`（`http-bridge.ts:321`）两条**互相独立**的推导：

```ts
status: run.status === "running" ? "failed" : run.status,
...(run.lastError ? { errorClass: "resource" as const, retryable: true } : {}),
```

静态看着像小问题。真跑一遍（起一个真 HTTP bridge，第一拍断连、之后报 completed）：

```
status     = "completed"      ← 后来正常完成了
errorClass = "resource"       ← 却说失败原因是资源问题
retryable  = true             ← 还说值得重试
终态事件    = "completed"
```

**三句话互相打架。** 引擎读到 `completed` 就认成功，
同时把 `retryable` 记进重修账 —— 一次普通网络抖动被算成了"可重试的失败"。

要害在 `lastError` 的**语义**：它记的是轮询途中的传输异常，
而那里的处理是 **"下一拍重试"**（`:224` 的 catch 分支写着
`Transient poll failures are ignored: the next tick retries`）——
**它从头到尾就没打算代表这次 run 失败了。**

判据改成 `run.lastError && run.status === "failed"`，与
`cli-agent.ts:374`（`lastKind === "failed" && run.exitCode === null`）**同源**。

> **同一个仓库里，两处写着一个意思、却用着不同判据。**
> `cli-agent` 判 `lastKind === "failed"`，`http-bridge` 判 `lastError`。
> 这正是"查全表"才看得见、而"盯着一个点"永远看不见的东西 ——
> 两边都单独看都成立。

### 22.48 又一条把缺陷钉住的既有测试

`http-bridge.test.ts` 里有一条
`轮询抛错时结果标成 resource/可重试`，断言的**正是上面那个矛盾形状**：

```ts
expect(result?.errorClass).toBe("resource");
expect(result?.retryable).toBe(true);
```

它一直是绿的。**因为它是照着实现写的，不是照着语义写的。**

判别方法很简单：把这条测试的标题念一遍 ——
"轮询抛错时结果标成 resource/可重试"作为**事实描述**通顺，
作为**应当如此的要求**不通顺（抖完了为什么要标成失败？）。
**标题读起来像事实陈述、而不是像要求，就是照抄实现的信号。**

已改判为 `轮询抛错不落 errorClass —— 抖动过去就过去了，不该留痕`，
并补三条守住另一侧。反向注入里专门有一条 `③ 永远不贴`，
它被"真失败才带 resource/可重试"咬住 ——
**只加"别乱贴"的断言等于允许"永远不贴"，那不是修好，是把功能删了。**

### 22.51 两条写测试的纪律（第九轮亲身踩的）

1. **跨异步边界的断言要轮询，不能写死 sleep**。这批用例跨了真实边界
   （POST /run 之后 run 才挂上审批）。写死一个 sleep 是在**赌机器快慢**：
   赌赢了是绿，赌输了是偶发红 —— 而偶发红会被当成"测试不稳定"忽略掉。
   这里赌的恰恰是"取消能不能解开一个卡死的 run"，赌注更大。
   （`waitFor()` 的注释里写明了这一点。）
2. **别用一个跟被测行为无关的信号去等条件**。我第一版等
   `/state` 的 `status === "running"`，而 `status` 只在 **`hello` 事件**里
   才变（`serveEmit:90`，`log`/`error`/`done` 都不改它）—— 发的是 `log`，
   于是条件永远不成立、超时。自己写的桩要发出跟真实 run 一样的信号，
   否则测的是一个不存在的事件流。
