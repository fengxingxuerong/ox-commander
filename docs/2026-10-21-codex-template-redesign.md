## 〇、为什么还要再来一轮

操作者两次给出同一句反馈：「桌面端的功能太少」（第一次见 ENGINEERING-LOG 的 M1 条目
动机段，2026-10-21；本次是第二次，针对的是 M1–M3c 落地之后的形态）。

第一轮（M1 → M3c-3，10-20 → 10-21）解决的是**单线程工作区的工作台手感**：三栏壳、
线程树、逐行 diff、行级评论、@ 文件补全、线程级沙箱/审批/模型/推理强度。这些做完之后，
对照 Codex 的整体产品形态，缺的已经不是「会话页好不好用」，而是**产品骨架级的四块**：

1. **多线程并行** —— Codex App 的自我定位是「智能体指挥中心」，指挥的对象是复数。
   我们桌面会话侧同一时刻只有一条活跃线程（`electron/ipc/chat.ts` 的 `live` 是模块级
   单例）。左栏线程树已经摆好了「复数」的样子，但复数只是历史，不是并发。
2. **Skills / MCP** —— Codex 的能力扩展面（技能包 + 90+ 插件 + MCP 共享配置）。
   我们的会话工具目录是硬编码六件套（read/grep/apply_patch/run_command/…），
   没有任何注入第三方能力的通道。我们是 MCP **server**（`headless/mcp.ts`），
   不是 client —— 能被集成，不能去集成。
3. **Automations** —— Codex 的触发式后台工作。我们的定时能力只在 headless serve
   （`headless/schedule-core.ts`：`--every` 自投递 POST /run），桌面端零入口 ——
   引擎有、界面没有，恰是 M1 动机里「引擎层资产比 UI 层多」的又一例。
4. **记忆 / 终端 / 浏览器视图** —— Codex 2026-04 大版本加的 Memory、终端视图、
   in-app 浏览器。我们对应位置分别是：静态约定注入（OX.md/AGENTS.md，不会学习）、
   `run_command` 的工具输出（无手动终端）、dev-server 预览保活 + 「在系统浏览器打开」
   （无应用内浏览）。

**定位判词的展开**（「编排为体、Codex 为用」）：

- **体**（不动）：PRD → zone 互斥 → 硬门禁 → 交付凭据 → 外部复核。这是命题出处，
  也是全部门禁判据的所在。本蓝图的一切新增都**不进编排器的验证链**。
- **用**（对标）：交互模版、信息架构、工作面能力以 Codex App 为参照系。
- **推论**（不学）：不学它的订阅生态、云端托管（Cloud 模式）、C 端拟人化。
  Codex 的对照组结论凡与 [2026-10-17 盘点](2026-10-17-competitor-gap.md)的 D 类决议
  冲突的，以 D 类为准 —— worktree 隔离、移动原生 App、「人挑 diff」维持不做。

## 三、信息架构重设计（IA-2）

### 现状的问题

现在的桌面是「编排器五页」：`projects（默认）→ prd-review → board → chat → settings`
（`src/types.ts` 的 `Page` 联合 + `HudNav.tsx`）。对照 Codex 模版有两处错位：

1. **不是 chat-first**。Codex 打开即线程工作区；我们首屏是项目登记表 ——
   「指挥中心」的叙事被一个「表单」挡在门口。会话页是五页之一，而不是家。
2. **Skills / Automations 没有家**。M5/M6 做完能力后，若塞进设置页二级 tab，
   等于把 Codex 的一级公民做成我们的配置项。

### 目标形态

顶栏收敛为 4 格 + 左栏承担项目/设置入口（Codex 同款布局逻辑）：

```
┌───────────────────────────────────────────────────────────────┐
│ OX  ║ 会话(默认) │ 编排 │ 自动化 │ 技能 ║      [状态点/待决策] │
├──────────┬──────────────────────────────────┬─────────────────┤
│ 项目列表  │  线程头: 沙箱/审批/模型/推理      │  改动审查        │
│ ──────── │  ────────────────────────────    │  ────────       │
│ 线程树    │  执行流(工具调用/审批/流式正文)    │  逐行 diff      │
│ ·活动状态 │  ────────────────────────────    │  行级评论        │
│ ·搜索     │  输入框(@ 引用)                   │  [终端] tab(M8) │
│ ──────── │                                   │                 │
│ 项目库⚙设置│                                  │                 │
└──────────┴──────────────────────────────────┴─────────────────┘
```

- **「编排」一格包两步**：需求确认（prd-review）与执行看板（board）在导航上合并为
  一个入口、页内两步走（先 PRD 后看板）。差异化资产不隐藏 —— 它只是从「五个之一」
  变成「会话之外的另一件事」。
- **「自动化」「技能」为新一级导航**（M5b / M6 各自带页面进场；导航格可以先落，
  页面未就绪时显示「引擎就绪、界面在建」的诚实占位，不摆假按钮）。
- **项目库与设置移到左栏底部常驻入口**（Codex 的设置就在左下角）。projects 页
  保留为管理面（登记/换根/删除），不再是默认页。
- **左栏升级**（M4 一并做）：每线程活动指示（running 转点 / 等待审批红点 / idle 静默）、
  跨项目「全部线程」分组、线程搜索 —— 补齐 M1 已知缺口（「左栏没有搜索与归档分组」）。

### 实现风险与取舍（两个方案）

- **方案 A（推荐，低风险）**：`Page` 联合不动，只改 nav 呈现与默认页
  （`projects → chat`），prd-review/board 由「编排」入口的页内 tab 导航。
  改动集中在 `HudNav.tsx`、`store.ts` 默认值（带旧版本持久化迁移：读出的旧默认值
  按现状回落）、`ui.test.tsx`/`router.test.ts` 口径。
- **方案 B（候选，高成本）**：真正合并 page 联合（`"orchestration"` 吃掉两页）。
  牵动 `check-exhaustive-maps`、持久化 schema、全部相关测试。收益仅是类型层面更干净。
  **判：先 A 后视情况 B**，B 不排期。

新增导航格的硬纪律：`scripts/check-exhaustive-maps.mjs` 要求每档登记（App.tsx 的
switch 有注释明说「靠 default 兜时新增 page 会静默渲染成 ProjectsPage」）——
IA-2 落地时必须同步登记，不吃 default。

## 四、里程碑规划（M4 → M9）

排序原则：**先并行（指挥中心的字面意思）→ 再能力注入（Skills/Automations/MCP）→
再增强视图（记忆/终端/浏览器/PR）**。每轮独立可验收；每轮完成后更新 README 能力表
与 CHANGELOG/ENGINEERING-LOG（既有纪律，不赘述）。

### M4 · 多线程并行 + IA-2 微调（最大的一轮，store 事件流改造是不确定项）

**目标**：同一项目多条线程可同时运行；左栏看得见每条线程的状态；默认页变会话。

**设计要点**：

- `electron/ipc/chat.ts` 的 `let live` 单例 → `Map<sessionId, Live>`；
  abort/resume/fork/delete 全部按 sessionId 寻址。`chat:*` 事件已带 sessionId，
  协议面不用动。
- **renderer 事件流是本轮最大工作量**：`src/store.ts` 现在默认「事件 = 我盯着的那条
  线程」。要改成：活跃线程事件照常渲染；非活跃线程事件只更新左栏状态位（running/
  等审批/新产出计数）与系统通知（`notify-rules.ts` 增「后台线程待审批」档 ——
  判据仍须纯函数可逐点审计）。
- **并行冲突（本蓝图的关键设计决策）**：Codex 用 worktree 物理隔离；我们 D 类决议
  不走 worktree。三候选：
  - P1 自由并行 + **冲突检测提示**：写文件前查 `FileJournal`/mtime，若该文件刚被另一条
    活跃线程改过 → 弹审批（「线程 B 三十秒前改过这个文件」），操作者放行才写。
  - P2 线程级 zone 声明：发线程时可划目录范围，越界提示（软约束，只提示不回滚 ——
    与编排侧 BatchGuard 的硬回滚是两种判据，**故意的**，要写进 ARCHITECTURE）。
  - P3 同项目写串行闸：第二条线程的写操作排队。
  - **判：P1 为默认，P2 为进阶开关，P3 不做**（把 Codex 的无摩擦手感删没了）。
    会话层的哲学是「人是最后的仲裁者」，编排层才是「门禁是仲裁者」—— 这正是
    「体/用」分工在最容易混淆的一处的体现。
- 并发上限与预算：默认同跑线程数上限（配置项，含 headless 口径）；token 用量按
  线程分列（`shared/usage-meter.ts` 已按调用记账，聚合面加 sessionId 维度）。
- IA-2 方案 A 同轮落地（默认页、导航 4 格、左栏活动指示 + 搜索）。

**验收**：两条线程同项目真模型并跑互不串台；后台线程的审批能弹系统通知并能切过去批；
中止一条不影响另一条；冲突检测对「同文件先后写」有可复现用例；site 审计新增位点全杀；
新 IPC 通道过 `check:ipc-channels`；旧持久化 store 升级不白屏（迁移用例）。

**前置**：M3c-3 WIP（推理强度）必须先提交合入 —— 两轮共享
`store.ts`/`ChatPage.tsx`/`shared/chat-events.ts`，在别人的未提交改动上开工 =
重演 2026-10-20 变异脚本抹掉未提交流式改动的事故。

### M5a · 线程侧 commit/push（对齐 F5）

**目标**：会话线程的改动可以从右栏导出为 git 分支 + commit（默认不 push，与编排侧
`git-export` 同哲学：永不 `--force`、不碰凭据）。

**设计要点**：复用 `electron/engine/git-export.ts` 的 Runner/staging 件；差别在输入源 ——
编排侧吃批次产物，线程侧吃 ReviewRail 的 (turn, path) 变更集（`shared/chat-changes.ts`
已经把它算清楚了）。不可撤销/超上限的改动照实列出并拒绝静默混入（M2 既有纪律）。

**验收**：真 git 仓库里两线程改动导出为两个分支；push 开关默认关；
「create 证据才肯删」不变量在线程侧同样成立（复用 `snapshot-store` 判据）。

### M5b · Automations 桌面化（对齐 F7）

**目标**：「自动化」一级页：定时任务列表（名称/spec/间隔/启用开关）+ 触发历史 +
忙跳语义可视化。

**设计要点**：

- 判定逻辑从 `headless/schedule-core.ts` **迁移到 `shared/`**（它本来就是纯逻辑：
  间隔解析/补跑判定/忙时重试间隔），headless 与桌面共用同一份 —— 分层红线要求
  （shared 零 node 内建，lint 强制），迁移时按既有「模块拆分红线」纪律保导入面兼容。
- 桌面装配：定时器在 `electron/` 层，触发 = 走既有 orchestration 单飞闸（409 语义
  原样保留：忙时跳过不积压，界面上写清楚「跳过了第 N 次，因为上一个还在跑」）。
- 触发历史落审计 JSONL（复用 `audit-log.ts`，2MiB 轮转已有）。
- **诚实边界**：Codex 的 Automations 是事件触发（issue/告警/CI/PR）；本轮先做
  **时间触发**（引擎现成）。事件触发（如 GitHub webhook → 本地 serve → 触发 run）
  列 M9 之后候选，蓝图不假装它便宜。
- Automations 的通知接 `notify-rules`：定时 run 出结论本来就在三类通知里，无需新档。

**验收**：桌面建一个每 60s 的演示 automation，跑两轮、忙跳一轮、重启补跑一轮，
四个事实都在触发历史里；headless 侧原有用例零回归（迁移不改语义的证明）。

### M6 · Skills（对齐 F6）

**目标**：`.ox/skills/<name>/SKILL.md`（项目级）+ `<userData>/skills/`（全局级）；
会话按需取用；「技能」一级页管理。

**设计要点**：

- **注入分三级**（防上下文爆炸，与约定注入的 8000 字符总预算纪律同族）：
  ① 常驻目录：name + description（front-matter），总预算封顶，截断说破原长度；
  ② 全文按需：新工具 `read_skill`（走沙箱读路径，realpath + 禁读密钥文件同判据）；
  ③ 资源文件：SKILL.md 里引用的相对路径由模型自己 `read_file`，平台不预载。
- 注入顺序沿用既有契约：任务描述 → 约定 → **技能目录** → 平台契约 → 操作者附言
  （约定块已声明「不覆盖契约」，技能块同款声明）。
- 桌面技能页：列表/启停/新建（模板起步）/打开所在目录。内置模板首批只做**零外部依赖**
  的：「跑本项目 verify 并解读失败」「生成发布说明（从 git log）」「issue 分诊
  （复用 IssuePicker 的取数）」。Figma/Linear/部署类 = 生态位留给 M7 的 MCP 与
  用户自写，**内置库不从零造集成**（那是插件市场的活，§五已判不做）。
- 读不动的技能只报不抛（约定注入同款纪律）。

**验收**：技能出现在会话系统上下文（转录可见）；`read_skill` 拿到全文；禁读路径
经技能目录穿不进去（安全用例：技能目录里放 `.env` 软链）；预算截断说破。

### M7 · MCP client（对齐 F8）

**目标**：会话能接第三方 MCP server（stdio 先行），工具并进工具循环。

**设计要点**：

- 注册形态学 `agents.d`：`mcp.d/<server>.json`（command/args/env），**只加载自己写的**
  （`execToken` 红线同款信任模型：外来 manifest 不进门）。env 走 `scopedEnv` 语义。
- 工具名空间 `mcp__<server>__<tool>` 并入 ToolSpec；单会话工具目录长度有上限，
  超限的技能页/界面说破（又是「截断说破」纪律）。
- **执行边界**：MCP 工具调用默认走审批三档（与 run_command 同口径）；返回内容过
  `redact`（脱敏）+ 截断上限；超时/熔断复用 TimeoutGate 与冷却表思想。
  MCP server 是外部进程 = 沙箱外，**平台不为它的行为背书** —— 这句话写进界面。
- 网络型 MCP（SSE/streamable HTTP）本轮不做，stdio 一种；判据先窄后宽。
- 与 `headless/mcp.ts`（我们是 server）互不干扰，两个方向都保留。

**验收**：接一个真实本地 MCP server（如文件系统 server）在会话内调用成功；
审批/脱敏/截断/超时各有用例；坏 manifest 被 skipped 并报给界面（agents.d 同款语义）。

### M8a · Memory（对齐 F13，显式形态）

**目标**：跨会话记忆的最小诚实形态：`.ox/memory.md`（项目级）+ `<userData>/memory.md`
（全局级），注入走约定同通道；模型可经新工具 `remember`（内容走审批）写入；
「记忆」在设置页可看可编辑可关。

**设计要点**：**不做隐式学习**（Codex Memory 的「自动记住纠正」需要成熟度与信任，
我们先做「显式写入 + 显式注入」，每一条记忆都在文件里、都能被人删）。
记忆块注入预算与约定共享 8000 字符池，超出说破。

### M8b · 沙箱化终端（对齐 F19 的终端半边）

**目标**：右栏加「终端」tab：操作者手动输入命令，走**与 run_command 完全相同的闸门**
（CommandPolicy + planSpawn + killTree + scopedEnv），输出流式回帖。

**诚实边界**：这不是 Codex 的真 PTY 终端 —— 是「沙箱化手动命令行」。白名单外的命令
被拒时界面给拒绝理由（判据可见）。`danger-full-access` 档可放开白名单但代码地板仍在
（既有语义）。做真 PTY（node-pty 依赖 + 无闸门交互）= 把「一切命令进出唯一闸门」的
架构红线砸了，**明确不做**。多文件视图：右栏已是按文件分组，加「工作区文件树浏览」
列可做·低（M9 候选，IDE 化方向要克制）。

### M9 · 收尾轮（可做档集中处理）

- **in-app 浏览器增强**（F15）：PreviewPanel 加地址栏/刷新/多 tab。导航边界：默认只
  允许已探活的预览地址 + 操作者手动输入的 URL；webview 进程隔离（Electron webview
  权限收紧到零 node 集成）。
- **PR 审查侧栏**（F18）：`github-context` 取 PR diff → 复用 ReviewRail 渲染；
  评论 = 生成 PR 评论**草稿**（复制/打开浏览器提交，不自动发 —— 与「CI 结论只回流，
  不自动重修」同哲学）。
- **弹出独立窗口**（F12）：线程 pop-out 成 BrowserWindow，事件流复用（多窗口
  broadcast 是 serve SSE 已有形态的桌面化）。
- diff 内联编辑（F23）、语音输入（F11）若届时仍值得做，从「可做」档取。

### 各轮共同纪律（不是新发明，全部沿用）

新 IPC 通道 → `check:ipc-channels` 登记；新 page/nav → `check-exhaustive-maps` 登记，
不吃 default；`store.ts` 变更 → site 审计全杀再提交；README/gates 数字 →
`check:doc-claims`；跑 mutation 前先 commit；新 id 生成带单调序数（全仓零
`Math.random`）；通知判据纯函数。

## 六、本蓝图不承诺的事

1. **不承诺时间表**。每轮工作量以实测为准；M4 的 store 事件流改造是最大不确定项
   （renderer 侧从「单活跃线程假设」到「多线程状态位」是口径变化，不是加功能）。
2. **不追 Codex 的周更**。它的 changelog 是周节奏（0.158.0 一版几十个条目）；
   逐条追 = 永远在后面跑。本蓝图对标的是**产品骨架**（2026-02 首发形态 + 04 大版本的
   非偏题项），此后回到「竞品刷新」既有的吸收节奏：每轮只取与命题兼容的格子。
3. **不承诺复刻生态**。订阅、云托管、市场规模三样复刻不了，也不试图复刻 ——
   我们的可接入性独占位（自带执行器池，不依赖订阅）恰好是 Codex 生态的反面。
4. **调研基线是宣称下界**。§一 的口径声明适用于全文：Codex「有」某功能以官方/第三方
   宣称取证，未做源码级核对（它也不开源桌面端）。
